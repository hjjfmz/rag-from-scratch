# 三服务改造方案（简化版）：SQLite 单体 → PostgreSQL + Qdrant + Redis

日期：2026-11-15。基线：`cdf362f`，分支：`codex/cli-dual-graph`。

本文是对 `service-storage-design.md`（下称"原方案"）的**范围收缩版**，取代原方案的范围约定。
技术方向不变（三个独立服务），砍掉原方案中面向多租户生产系统的机制（租约、代数、补偿任务、
40 条标注题评测等），理由逐条见 §7。

## 0. 人话版导读（先读这一节就够了）

**现在的问题**：整个系统（资料、向量、会话）都塞在本地的小文件（SQLite）里。每次有人提问，
程序把**所有**资料整个搬进内存从头翻一遍再回答。资料少没事，一多就又慢又吃内存，
面试被问"数据量大了怎么办"就答不上来。

**要改成的样子**——把存储拆成三个独立软件，各司一职：

- **PostgreSQL（PG）＝ 账本 + 书架**。所有原文、条目、关系记在这里。一本书"存在不存在"，
  以它为准。
- **Qdrant ＝ 卡片索引柜**。每篇资料做一张"内容卡片"，提问时它飞快翻卡片，报出
  "内容最像的 100 张卡片编号"，但它不管书本身。
- **Redis ＝ 便利贴**。问过的问题和答案贴桌上，同样的问题再来直接抄便利贴，不用重算。

**四个关键概念：**

1. **有界召回 = 不再全馆翻书。** 现在是每来一个问题把每本书翻一遍算相似度；改后是先查
   卡片柜拿 100 个编号，只从书架取这 100 本看原文。自己手写的"算相似度公式"不删，
   留着做对照实验（小数据集上自己全算一遍，看卡片柜的 100 本里捞回了几成真货），
   这反而是面试亮点。
2. **PG 为准的最终一致 = 账本说了算。** PG 和 Qdrant 是两个独立软件，没有"两边同时成功
   或同时失败"的保证。解决办法：卡片柜报来的每个编号都回 PG 验一下"这书真在吗"，
   不在就丢掉。所以：断电导致卡片多贴了 → 取书时发现没这书 → 丢卡，永远不出错；
   卡片少贴了 → 那篇暂时搜不到，但绝不会答错。不需要为此造任何清理系统。
3. **事务切换版本 = 换书不会换到一半。** 更新一篇文档时，新内容要么全部写入成功、
   要么保持旧版原样，这是现在就有的能力，平移到 PG 即可。原方案里"任务租约、版本代数"
   那一堆是为"很多人同时写不打架"设计的，单人使用根本不会打架，砍。
4. **BM25 的坑 = 唯一要小心的地方。** 关键词检索的打分公式是自己手写的（面试卖点，
   绝不能改）。公式里有一项"这个词在全馆有多稀有"——改完后如果只按桌上的 100 本候选算
   稀有度，同样的问题得分就会变，等于算法行为变了。解决办法：导入时提前把
   "每个词在多少本书里出现、全书平均长度"记成一张表，打分时照抄全局数字，
   公式一分不改，结果与改造前完全一致。

**"手写算法绝不动"怎么保证**：算法吃的"原料"从"全馆的书"换成"桌上 100 本候选"，
但打分、排序、找关联、多文件分配名额的逻辑一行不改。证明方式：项目里现成的一套自动
测试改造前后各跑一遍，结果必须逐条一致；再加一组对拍——同一批小资料用"老办法全馆翻"
和"新办法查卡片柜"各跑一遍，六种检索模式结果对比。

**为什么砍原方案**：参考的开源项目是多人使用的商业产品，要管账号、权限、多人并发上传，
所以需要任务队列、租约那些机制——都是为了"多人不打架"。单人演示项目没有"多人"，
那些机制就是给不存在的问题造方案，每个还要写一堆代码和测试去伺候。

---

**两条铁律：**

1. **手写算法零改动。** 所有公式、融合、排序、图扩展逻辑逐行不动，改动方式是"换数据来源"
   而不是"换实现"。保护清单见 §6，等价性论证见 §6.2。
2. **基础设施做减法。** 原方案里每一个为并发多写者设计的机制，在单用户单写者场景下都被
   更简单的已有机制覆盖。不做面试讲不清、测试养不起的东西。

## 1. 目标与非目标

### 目标

- 把当前的单机存储拆为三个独立服务组件：
  - **PostgreSQL**：来源、片段原文、实体、关系、BM25 词项统计、会话——即"账本与正文"。
  - **Qdrant server**：片段/实体/关系三类向量，只负责"给我最像的前 N 个 ID"。
  - **Redis**：答案缓存。
- CLI 十个命令（`cli.py:42-65`：ingest / sync / query / search / agentic-query / list /
  delete / graph / doctor / eval）、六种检索模式、现有 pytest 全部保持工作。
- 面试叙事成立：为什么拆、一致性怎么处理、哪些是手写算法。

### 非目标（明确不做）

- 多租户、独立 Worker 进程、任务租约令牌、知识库代数、查询快照租约、补偿清理任务系统。
- 40 条标注题评测、冷/热缓存耗时矩阵、Prometheus 指标、资源观测矩阵。
- 新框架依赖：不引入 LangChain、SQLAlchemy、Alembic、官方 qdrant-client（用已有的
  `requests` 直连 Qdrant REST，与项目"从零手写"的调性一致，还少一个依赖）。

## 2. 现状盘点（改什么、为什么）

### 2.1 现在一条查询怎么跑（全量快照模式）

1. `rag/graph_service.py:60-61`：`_snapshot()` 调 `store.records()`，后者
   （`rag/knowledge_store.py:132-145`）把**全库**的 sources / chunks / entities / relations
   一次性读进内存。
2. `rag/graph_retrieval.py:69-71`：`DualLevelRetriever` 构造时把快照全部装进 Python 字典。
3. vector 通道（`:95-99`）：对**每一个** chunk 手算余弦相似度，排序后取前 `budget` 个。
4. keyword 通道（`:101-104`）：**每次查询**对全量 chunk 现场新建一个 BM25 索引
   （`bm.index(documents)` 写在 `search()` 里面），再搜索。
5. local 通道（`:105` 起）：全量扫描实体表做名称匹配找种子实体。
6. 图扩展（`:114`）：全量扫描关系表找种子的一跳邻接。
7. global 通道（`:126` 起）：全量扫描关系表打分选种子。

问题：内存占用随库线性增长；每次查询重建 BM25 是 O(N)；面试时讲不出"存储服务化"。

### 2.2 存储现状：其实是三个 SQLite + 一个 JSON

| 数据 | 位置 | 使用方 |
| --- | --- | --- |
| 知识库（来源/片段/图谱） | `rag/knowledge_store.py`（SQLite） | CLI |
| 会话（sessions/messages 两表） | `backend/session_manager.py:11-12`（sessions.db） | Web |
| 模型调用缓存 | `rag/model_client.py:111-117`（可选 SQLite 文件） | 两者 |
| Web 向量索引 | `rag/vector_store.py:183-199`（save/load 整个 JSON 文件） | Web |

### 2.3 两套检索栈（简化版的并栈决定）

- **CLI 栈**：`GraphService` + `DualLevelRetriever`，六模式，数据在 SQLite。
- **Web 栈**：`RAGPipeline`（`rag/pipeline.py`）+ `VectorStore`（内存 + JSON 文件）+
  `Retriever`（`rag/retriever.py:38`，三模式），在 `backend/api.py:17-24` 接线。

**决定：Web 迁到 GraphService，删除双栈。** 这本是原方案 §7 的意图，此处保留。
理由：面试讲"一套服务层，CLI 与 Web 复用"远好于"两套各自为政"；且 Web 栈的
JSON 文件向量库正是要被 Qdrant 替代的对象。退役方式见 §6（是删调用链，不是改算法）。

| 组件 | 职责 | 对应现状 |
| --- | --- | --- |
| PostgreSQL | sources / chunks / entities / relations 四表**原样平移**
  （`knowledge_store.py:20-44` 的 schema）；新增 BM25 词项三表（§4.4）；

| Python 应用 | 业务编排 + **全部手写算法**（§6）+ Qdrant REST 客户端 | 不变 |

## 4. 关键设计，逐个说清楚

### 4.1 Qdrant"有界召回"是什么意思

**现状**：想知道哪本书和问题最相关，就把图书馆里每本书都翻一遍
（`graph_retrieval.py:95-99` 对每个 chunk 算一次余弦）。

**改后**：先问图书管理员要"最像的 100 张卡片编号"，再去书架取这 100 本书。
向量全部放 Qdrant；查询时拿回 top-N 的 **ID 和相似度分数**（N 沿用现有预算公式
`min(top_k*4, 100)`，`graph_retrieval.py:94`），原文再用这些 ID 从 PostgreSQL 按
主键读出——只读候选，不读全库。

**手写余弦不删除**：`cosine_similarity`（`rag/vector_store.py:38`）保留，作为
"精确基准"对照模式——小语料上用手写余弦全量算一遍，对比 Qdrant 召回了多少真候选，
写进评测报告。这是面试亮点（索引召回 vs 精确召回的消融），不是遗留代码。

### 4.2 "PG 为准的最终一致"是什么意思

**问题**：PG 和 Qdrant 是两个独立服务，**没有跨库事务**——不可能让"两边同时成功
或同时失败"。导入时写完 PG、写 Qdrant 时进程挂了怎么办？

**方案**：PG 是**账本**，Qdrant 是**索引卡片盒**。一条知识"存不存在"永远以账本为准：
Qdrant 报来的每个候选 ID，都必须回 PG 查到有效原文才算数；PG 里查不到 → 直接丢弃。

**推论（这就是为什么不需要原方案的补偿任务系统）：**

- Qdrant **多写了**（PG 事务回滚了但向量已 upsert）→ 这些孤儿向量最多浪费一个候选
  名额，**永远不会进入任何回答**——因为回 PG 验证这一步把它们天然过滤掉了。
- Qdrant **少写了** → 该文档暂时搜不到（漏报），但**不会出现错误数据**。

所以正确性不依赖任何清理机制。孤儿向量只在导入收尾时"尽力删"（一条按 source 过滤的
delete），失败就留着，无害。删除文档同理：PG 事务删行（`knowledge_store.py:124-130`
的语义平移）→ 立即不可见 → Qdrant 侧异步尽力清理。

这就是"最终一致"的准确含义：**两个服务短暂不一致的窗口期内，系统对外行为仍然正确，
因为裁决权单方面在 PG**。面试时把这句和上面的推论讲清楚，比一套租约机制加分得多。
诚实的边界说明：本方案是单写者、单机部署，不宣称跨存储原子提交。

### 4.3 "事务内切换版本"是什么意思（现有机制，原样平移）

现状**已经有**这个保证：`replace_source`（`rag/knowledge_store.py:77-122`）用
`BEGIN IMMEDIATE` 单事务完成"写新片段/实体/关系 + 原子换掉 sources 行"，任何一步失败
整体回滚，旧版本原样保留（`:78` 的注释和 `:83-84` 的修订冲突检查就是这个语义）。

PG 版把这套 SQL 原样换成 psycopg，事务语义只会更强（PG 是真 MVCC 事务，SQLite 靠
文件锁）。导入期间查询看到的要么是完整旧版、要么是完整新版，不存在中间态。

原方案的"知识库代数 / 任务租约 / 查询快照租约 / 旧版本清理等待"是为**多个写者并发**
不互相踩踏设计的。本项目单用户单写者（一次只有一个导入在跑），上面这个单事务就是
全部正确性保证，其余机制砍掉（§7）。

### 4.4 BM25 词项持久化（唯一需要新设计的部分，公式零改动)

**现状**：每次查询在 `search()` 里对全量 chunk 现建 BM25（`graph_retrieval.py:101-104`），
IDF、平均文档长度每次都临时算。

**改后**：导入时调用现有的 `tokenize`（`rag/bm25.py:65`）把词项写三张表：

| 表 | 内容 | 回答的问题 |
| --- | --- | --- |
| `chunk_terms(chunk_id, term, tf)` | 谁的文档里哪个词出现几次 | 粗筛：哪些 chunk 含查询词 |
| `term_df(term, df)` | 全库多少文档含该词 | IDF 分子分母 |
| `corpus_meta(n, avgdl)` | 文档总数、平均文档长度 | 长度归一化 |

查询两步走：

1. **粗筛（SQL）**：含任一查询词的 chunk_id，按词频和排序取窗口 500 个（超出则截断，
   丢弃数写进检索轨迹）。
2. **精排（Python）**：窗口内候选 + **全库统计**（df、n、avgdl 从表里读）喂给现有
   BM25 打分。

**关键正确性细节**：IDF 和 avgdl 必须来自全库统计，**不能**用候选子集现算，否则
同一查询的分数和改造前不一致——这违背"算法零改动"。

**bm25.py 的处理（唯一允许的接触点）**：新增一个纯计算辅助入口 `idf_for(df, n)`，
`index()`（`:135`）内部改为调用它。这是一行等价重构：公式本体不动、输入输出逐位一致，
由现有 `tests/test_bm25.py` 全量回归锁定。`_score_document`（`:180`，BM25 公式本体）、
`search`（`:225`）、`reciprocal_rank_fusion`（`:266`，RRF）一行不动。
（备选：若坚持 bm25.py 一行不碰，则在存储侧复制这一行 IDF 公式，并加对拍测试保证与
`index()` 一致。默认取前者，面试讲"等价重构 + 回归锁定"更体面。）

### 6.2 等价性论证（怎么做到"改存储不改算法"）

`DualLevelRetriever` 的输入是一个 `{chunks, entities, relations}` 字典。改造前后
**字典的形状完全相同**，差别只在内容范围：改造前 = 全库，改造后 = 召回窗口 + 其一跳
邻接。算法代码看到的输入格式不变，因此逐行不改。改造的本质是：

> 把"预先把全库搬进内存"换成"按需取窗口"，算法在窗口上的运算逻辑与原来在全库上
> 完全一致。

三处差异需要明确论证：

| 通道 | 原来 | 改后 | 差异定性 |
| --- | --- | --- | --- |
| vector | 全量余弦排序取 top-100 | Qdrant HNSW 近似召回 top-100 | 近似性差异（可调 ef 参数）。用精确余弦基准对拍覆盖率，写进评测报告——这是特性不是缺陷 |
| keyword | 全量 BM25 排序后截 top-100 | SQL 粗筛窗口 500 → 窗口内 BM25 精排（全库统计） | 窗口未截断时结果一致；截断时轨迹记录丢弃数。面试级语料（数百 chunk）几乎不触发 |
| local/global 种子 | 全量扫描后 Python 判定 | SQL 粗筛（LIKE/向量）→ 原 Python 判定函数精筛 | `_name_match` 等判定函数原样复用，SQL 只做粗筛，判定权仍在原函数。取到的种子集合与全量扫描一致（粗筛是超集） |

**回归保障**：现有 `tests/test_graph_retrieval.py`、`test_graph_service.py`、
`test_retriever.py` 等全部继续跑（SQLite 适配器）；另加一组"有界化对拍"测试：
同一份小语料，全量快照路径 vs 有界路径，六模式结果逐条一致。

## 8. 实施顺序（每步有回归门）

1. **抽边界**：`GraphService` 对 store 的调用收敛到 §5 的接口方法；pytest 增加

   门：pytest 全绿；smoke 确认 PG 建库/导入/查询可用。
3. **Qdrant 双写**：ingest 在 PG 提交后 upsert 三类向量；查询暂不动（向量仍走快照路径）。
   门：pytest 全绿；smoke 确认三个 collection 有数据、指纹隔离生效。
4. **检索有界化**：六通道改为"召回 → 候选 dict"；加对拍测试（§6.2）。

   门：`test_bm25.py` 全绿（锁定重构逐位一致）+ keyword 通道对拍一致。

   门：pytest 全绿；smoke 验证缓存命中/失效/Redis 宕机降级三条路径。

## 10. 面试叙事（三问三答）

- **为什么拆？** 现在全量快照加载（给出 §2.1 的行号证据），内存与查询时间随库线性
  增长；拆后向量召回在 Qdrant、候选按主键回 PG、词项粗筛在 SQL，查询成本只与候选
  窗口相关，与库大小解耦——§9.5 的实测数据佐证。
- **一致性怎么处理？** PG 为准的最终一致（§4.2）：账本裁决可见性，孤儿向量天然不可见，
  单事务切换版本（§4.3）；诚实说明边界——单写者、无跨库事务、不做高可用。
- **哪些是手写的？** §6.1 的保护清单；"算法行为逐位一致"由对拍测试证明（§6.2），
  而不是靠嘴说。
